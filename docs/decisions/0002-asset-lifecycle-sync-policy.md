# ADR-0002：资产生命周期与同步策略

- 状态：`accepted`
- 日期：2026-08-09
- 确认时间：2026-08-09T18:45:40+08:00
- 确认方式：用户明确回复“确认这四点”
- 范围：生成作业、资产注册、Git、云端同步和 BomboAdventure 发布
- 替代：无
- 被替代：无

## 背景

Studio 会产生大量随机化候选、预览、GLB、GIF 和帧。如果所有输出都进入 Git，仓库会迅速增长；如果全部只在本地，又无法恢复根源资产、正式里程碑和游戏发布版本。用户需要知道资产何时、由什么生成，并能方便且安全地清理。

## 决定

采用“默认本地、显式晋级、发布分离”的策略：

1. 每次生成创建带 UUID 的运行目录和 `run.json`。
2. 候选与缓存默认位于 Git 忽略的 `workspace/`。
3. 根源资产、代码、Schema、Recipe、正式清单和人工晋级的里程碑才进入 Git。
4. 大型正式二进制在仓库增长到需要时使用 Git LFS；不把所有生成物自动交给 LFS。
5. BomboAdventure 只消费带版本号的发布资产包，不直接依赖 Studio 工作目录。
6. 清理器默认 dry-run，展示文件数、体积、状态和依赖；里程碑、发布包引用或 `pinned` 的运行受保护。

## 原因

- 本地候选数量可能非常大，但绝大多数没有协作或长期保存价值。
- Git 适合代码、合同和有意晋级的版本，不适合无限累积的程序生成文件。
- 显式晋级能让“是否同步”成为可审计决定，而不是由文件扩展名偶然决定。
- 游戏消费发布包，可以让 Studio 自由演进而不破坏游戏工程。

## 运行记录最低合同

```json
{
  "schema": "assetsstudio_run_v1",
  "run_id": "uuid",
  "created_at": "ISO-8601",
  "asset_type": "humanoid.top",
  "generator": {"id": "...", "version": "...", "git_commit": "..."},
  "recipe": {"schema_version": 1, "seed": 0},
  "sources": [{"asset_id": "...", "sha256": "..."}],
  "outputs": [{"path": "...", "role": "preview", "bytes": 0, "sha256": "..."}],
  "status": "candidate",
  "storage_policy": "local",
  "pinned": false
}
```

## 清理规则

- `cache`：可随时清理。
- `rejected`：默认保留一个可配置期限后允许清理。
- `candidate`：未审查时不自动删除，除非用户明确设置期限。
- `promoted`、`release`、`pinned`：禁止普通清理。
- 有下游依赖的运行：必须先处理依赖关系。
- 所有清理都写入本地审计日志；正式内容删除还要更新 `docs/REMOVALS.md`。

## Git 与云端边界

| 内容 | 默认策略 |
| --- | --- |
| 源代码、文档、Schema、Recipe | 普通 Git |
| 根源模型、正式里程碑 | 明确登记后 Git；规模增长时迁移到 LFS/对象存储 |
| 小型 Gallery/GIF 审查证据 | 随对应正式里程碑同步 |
| 随机候选、帧序列、临时 GLB | 本地，不进入 Git |
| 游戏发布资产包 | 明确发布后上传，不在每次生成时提交 |

## 影响

- Studio 必须实现运行注册表、生命周期状态和清理器。
- Git 提交前验证器应拒绝未登记的生成二进制。
- 未来可能需要 Git LFS 或对象存储，但第一版不必先搭建云资产平台。
- 换机只能自动恢复已晋级/已发布内容；本地候选若未导出或同步则不会恢复，这是有意设计。

## 被放弃方案

- 所有生成物提交 Git：历史不可收缩，仓库会持续膨胀。
- 所有二进制都放 Git LFS：仍会消耗存储和带宽，也无法替代生命周期管理。
- 完全不保存生成元数据：无法复现、追溯或安全清理。
- BomboAdventure 直接引用 Studio 路径：两个工程生命周期耦合，换机和发布容易失效。

## 验证与复审条件

在 Phase 1/2 用真实 Actor、一个服装候选和一次随机发型运行验证目录体积、重建能力和清理体验。若实际结果不能满足预览、追溯或清理需求，创建替代 ADR；若发布规模或多人协作需求出现，重新评估 LFS/对象存储。
