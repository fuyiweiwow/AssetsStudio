# AssetsStudio 开发管理基准

- 状态：`active`
- 生效时间：2026-08-09

本文件把 `PRINCIPLES.md` 转换为每次开发都能执行的流程。

## 文档地图

| 文档 | 用途 | 更新时机 |
| --- | --- | --- |
| `PRINCIPLES.md` | 不轻易变化的开发原则 | 原则确实变化时 |
| `docs/PRODUCT_TECH_BASELINE.md` | 产品目标、阶段范围和当前技术基线 | 需求讨论或架构基线变化时 |
| `docs/ART_DIRECTION.md` | 当前美术风格、Actor结构基准与视觉验收边界 | 美术方向或视觉基准变化时 |
| `docs/features/*.md` | 每个主要功能的当前设计与历史 | 开始功能、改变方案、完成验收时 |
| `docs/decisions/*.md` | 跨功能或难以逆转的技术决定（ADR） | 决定被提出、接受、替代或撤销时 |
| `docs/DEVELOPMENT_LOG.md` | 重要开发检查点时间线 | 每个有意义检查点 |
| `docs/REMOVALS.md` | 删除和退休内容的审计记录 | 删除发生的同一检查点 |
| `docs/MILESTONES.md` | 当前资产里程碑 | 资产晋级或替换时 |
| `docs/ASSET_STATUS.json` | 机器可读资产状态 | 与里程碑同步 |

## 主要功能的判定

满足任一条件即视为主要功能：

- 新增用户可见的完整操作路径；
- 新增或改变模型生成、绑定、随机化、渲染或导出流程；
- 引入新的框架、运行时、文件格式或外部依赖；
- 改变多个模块共享的数据合同；
- 替换当前里程碑或正式技术方向。

小型修复可记录在已有功能文档的变更历史中，不必新建功能文档。

## 主要功能开发流程

### 1. 开始前

1. 阅读必读文档和相关资产工作流。
2. 从 `docs/templates/FEATURE_TEMPLATE.md` 创建功能文档。
3. 将状态设为 `proposed`，写明需求证据、范围、非目标和验收条件。
4. 技术选型至少比较一个合理替代方案，并记录选择原因。
5. 若决定跨越多个功能或未来替换成本高，从 ADR 模板创建决策记录。

### 2. 实现中

1. 实验文件只进入 `workspace/`。
2. 在小而可验证的检查点提交代码、文档和必要资产。
3. 实际实现偏离文档时，先把功能文档更新为真实状态，再继续扩展。
4. 新增模型或二进制资产时检查来源、许可证、大小和重建路径。
5. 视觉功能必须持续生成 Gallery/GIF，不以文字描述代替人工审查。

### 3. 变更技术方案

在功能文档的“技术决策历史”追加记录，包含：日期、旧方案、新方案、触发证据、变更原因、迁移影响。不要覆盖旧结论，使其看起来从未存在。

若旧 ADR 被替代，将旧 ADR 状态改为 `superseded`，并互相链接新旧 ADR。

### 4. 删除或退休内容

删除前确认：

- 当前正式入口已经不再引用它；
- 有替代项，或已经确认该功能不再需要；
- Git 历史、历史分支或外部归档可以恢复；
- 许可证要求不阻止删除或保留。

删除动作与 `docs/REMOVALS.md`、相关功能文档、索引和验证器更新应在同一开发检查点完成。

### 5. 完成与晋级

只有同时满足以下条件，功能状态才能设为 `accepted`：

- 验收条件逐项有证据；
- 自动测试或验证通过；
- 视觉功能通过用户人工审查；
- 当前限制与后续事项已经记录；
- 文档、时间线、资产状态和 Gallery 均已同步；
- 工作树没有不明来源的输出文件。

## 保存与时间线

- Git 提交记录精确的代码与文件时间线。
- `docs/DEVELOPMENT_LOG.md` 只记录重要检查点，不机械复制每个提交。
- 推荐提交格式：`type(scope): summary`，例如 `feat(preview): load actor GLB`、`docs(governance): establish development baseline`。
- 每次准备让用户审查、切换主要方向、清理旧实现或结束一段工作前，应创建提交并更新开发日志。
- 未验证的工作可以提交到开发分支，但不得标记为正式里程碑。

## 完成定义

一项开发工作只有在代码/资产、功能文档、决策记录、验证、人工审查入口和时间线彼此一致时才算完成。任何一项缺失都应明确标记为 `draft`、`proposed` 或 `provisional`。
