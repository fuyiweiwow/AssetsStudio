# AssetsStudio 产品与技术基线

- 状态：`accepted_baseline`
- 建立时间：2026-08-09
- 确认人：用户与 Codex

本文件用于同步“我们要做什么、为什么做、准备怎样做”。基线已经确认；后续变化必须写入功能文档或 ADR 并说明原因。

## 我理解的产品目标

AssetsStudio 是一个面向 2D/像素化 Rogue 类游戏资产生产的本地工作流工具。它复用已验证的 Actor、骨骼动画、发型、五官、短袖、短裤和鞋里程碑，让用户能够预览、组合、参数化和随机化角色外观，并由 Blender 生成权威 3D 结果以及最终 Gallery、GIF、帧序列或像素素材。

它不是一个通用 3D 建模软件，也不以电影级真实布料模拟为首要目标。核心价值是：换机器仍可复现、可批量生成、结果直观可审查、适合最终 2D 游戏表现。

产品美术方向固定为 Q 版日漫 JRPG。当前以《零之使魔》的轻幻想、明快气质和《闪之轨迹》的服装层次、角色可读性作为抽象风格坐标；结构真相仍是当前 Actor V1。完整边界和验收问题见 [`ART_DIRECTION.md`](ART_DIRECTION.md)。

## 已明确的需求

1. 保留并使用当前正式身体、Walk/Run、发型、五官、短袖、短裤和鞋模型及工作流。
2. 对资产调参或随机生成后，在同一页面中看到结果，并且必须能把资产放在当前 Actor 身上检查实际效果。
3. 前端使用 Three.js 显示角色和服饰的交互式 3D 预览。
4. 支持发型、五官和服饰的组合与可复现随机化。
5. 每次生成都应记录时间、配方、随机种子、来源、生成器版本、输出和审查状态，并能安全批量清理。
6. 默认生成结果只存在本地；只有根源性资产、正式里程碑或用户明确标记的发布资产才同步到云端。
7. Studio 最终服务于 BomboAdventure：先提供人形角色，未来可扩展到其他生物、地图及更多美术资产。
8. 未来支持服装配方参数，例如袖型与袖长、领型与领口面积、下摆长度、材质和花纹；裤子和鞋采用同一可扩展思想。
9. Blender 负责权威几何生成、贴合、绑定、动作验证和最终渲染。
10. 每个视觉结果提供正面、侧面、背面以及运动 GIF，用户人工审查是正式晋级条件。
11. 正式仓库携带工作流依赖的模型、纹理、动作和重建脚本，避免环境迁移后依赖 AssetsLab。
12. 正式分支保持短小、当前和可追溯，过时实现及时清理并留下原因与恢复位置。
13. 所有角色资产必须服务于统一的 Q 版日漫 JRPG 美术方向，并在当前 Actor 上通过多视角和动作人工审查。
14. Studio 使用“选择模型 → 选择骨骼 → 选择动画 → 拼装部件 → 结果预览”的工作流；当前只有一套模型、骨骼和 Walk 时如实显示单选，未来再扩展导入、绑定和重定向。

## 预览速度合同

“页面上马上预览”分成两级，界面必须明确告诉用户当前是哪一级：

1. **交互预览**：已有组件切换、颜色/材质、允许范围内的缩放与组合直接在 Three.js 中完成。模型加载完成后应接近即时反馈。
2. **生成预览**：改变拓扑、贴合、骨骼权重或需要 Blender 计算的参数，提交本地后台作业；页面显示排队、运行和完成状态，完成后自动替换 Actor 上的 GLB。允许等待数秒到数分钟，但不能让用户离开当前页面寻找文件。

Three.js 预览用于决策反馈；Blender 输出和多视角 GIF 才是正式审查依据。二者不能伪装成完全等价。

## 资产生命周期建议

每次生成建立独立 `run_id` 和 `run.json`，至少记录：

- `created_at`、`generator`、`generator_version` 和 Git 提交；
- Recipe、随机种子、Actor/源资产 ID 与内容哈希；
- 输出路径、文件大小、SHA-256、预览图与父子关系；
- `candidate`、`reviewed`、`promoted`、`rejected` 等状态；
- `local`、`sync`、`release` 存储策略；
- `pinned`、保留期限和清理原因。

清理必须以注册表为依据，先显示将释放的空间和受影响项目，再执行可恢复删除。被里程碑、发布包或其他资产引用的运行不能直接删除。

建议分层：

| 层 | 默认位置 | Git/云端策略 | 清理策略 |
| --- | --- | --- | --- |
| 根源资产 | `milestones/`、经批准的 `references/` | 必须显式登记并同步；大二进制未来可使用 Git LFS | 不自动删除 |
| 代码、Recipe、Schema、清单 | 正式源码目录 | 普通 Git 同步 | 随版本维护 |
| 生成候选 | `workspace/runs/<run_id>/` | 默认忽略，不上传 | 可按时间、状态、体积清理 |
| 可再生成缓存 | `workspace/cache/` | 永不上传 | 可随时清理 |
| BomboAdventure 发布包 | `workspace/packages/` 生成，发布后登记 | 仅明确发布版本上传到 Release/LFS/未来对象存储 | 本地副本可重建 |

不要把“生成过”自动等同于“应该进入 Git”。同步必须是一次显式晋级动作。

## BomboAdventure 集成边界

BomboAdventure 不直接读取 Studio 的工作目录，而是消费带版本号的资产包。资产包包含游戏需要的 Sprite Sheet、帧、元数据和许可证/来源摘要；调试用 GLB 只在确有需要时包含。

Studio 的作业、注册、审查和发布基础设施可以复用于其他生物和地图，但生成器本身必须按资产类型插件化：`humanoid`、未来 `creature`、`map` 使用各自的输入合同与验证器。地图不是“衣服系统再加几个参数”，不能强行共用同一几何流程。

## 明确不承诺的能力

- 不承诺任意外部服装自动完美适配任意体型；每个身体族必须有骨架、包络和服装模板合同。
- 不承诺所有拓扑变化都能浏览器即时生成；复杂变化必须等待 Blender 作业。
- 不承诺单一节点编辑器能够覆盖人形、生物和地图的全部生成逻辑。
- 不承诺自动检查可以替代最终人工视觉判断。

## 已确认的产品边界

用户于 2026-08-09 明确确认以下四项：

1. 接受“即时交互预览 + 等待 Blender 的生成预览”两级模式。
2. 接受候选默认本地，只有根源、里程碑和发布资产显式同步。
3. 接受 BomboAdventure 只读取版本化发布资产包，不直接依赖 Studio 工作目录。
4. 接受先完成人形角色，其他生物和地图以后作为独立生成插件加入。

对应跨功能决策已经固化为 `docs/decisions/0002-asset-lifecycle-sync-policy.md`。

## 当前非目标

- 第一阶段不实现完整 Blender 替代品。
- 第一阶段不追求实时高精度布料动力学。
- 在配方数据结构稳定前，不优先开发复杂节点/蓝图编辑器。
- 不把自动穿模分数当作最终视觉验收。
- 不把旧 GarmentCode 失败实验重新引入正式基线；以后若重启该方向，必须以新功能提案和新证据开始。

## 建议的交付阶段

### Phase 0：开发基准

建立原则、功能文档、ADR、删除记录、时间线和自动验证。本文档对应此阶段。

### Phase 1：Studio 外壳与资产注册表

建立本地前端工程，读取统一资产清单，展示六类里程碑、状态、来源、预览和已知限制。先让“现在有什么”稳定可见。

### Phase 2：Three.js 角色预览

把权威 `.blend`/`.fbx` 通过可复现脚本导出为预览用 `.glb`，在前端加载 Actor、服饰和骨骼动画，支持镜头、正侧背视图、播放/暂停和组件开关。

### Phase 3：配方合同与表单编辑器

先用普通控件定义稳定的角色配方 JSON：随机种子、发型、五官、上衣、裤子、鞋、颜色和参数。验证合同后再考虑节点表示。

### Phase 4：Blender 作业桥接

本地服务接收配方，调用 Blender 无界面脚本，返回模型、验证报告、Gallery 和 GIF。作业应有日志、状态、可取消性和确定性输出目录。

### Phase 5：程序化模块扩展

逐项完善发型、五官、衣服、裤子和鞋的参数化与随机化。每类资产都沿用候选区、自动验证、人工审查、里程碑晋级的闭环。

### Phase 6：节点/蓝图编辑器

当配方字段和模块接口稳定后，再把同一数据合同映射为节点编辑器；节点层不重新定义一套与表单不同的业务模型。

### Phase 7：2D/像素导出

固化摄像机、灯光、动作、方向、帧率、像素化和打包规范，导出游戏可直接使用的帧、Sprite Sheet、GIF 和元数据。

## 建议技术选型

| 层 | 建议 | 原因 | 主要替代方案 |
| --- | --- | --- | --- |
| 前端语言/构建 | TypeScript + Vite | 类型约束配方与资产合同；启动快；适合本地工具 | JavaScript；Next.js |
| UI | React | 适合参数面板、资产库、状态视图和后续节点编辑 | Vue；原生 Web Components |
| 3D 预览 | Three.js，经 `@react-three/fiber` 集成 | 保留 Three.js 生态，同时让场景状态与 React UI 协同 | 直接 Three.js；Babylon.js |
| 节点编辑 | 后期评估 React Flow | 与 React 集成成熟，但应等配方合同稳定 | Rete.js；自建 Canvas |
| 本地服务 | Python + FastAPI | 可直接复用 Blender/Python 脚本，类型和作业 API 清晰 | Node 服务；仅 CLI |
| 权威生成 | Blender 无界面模式 + Python | 当前里程碑与脚本已经建立在 Blender 上 | 浏览器端几何；游戏引擎编辑器 |
| 预览格式 | GLB/glTF | 浏览器加载、骨骼动画和材质支持成熟 | FBX 在线加载；OBJ |
| 权威源格式 | `.blend` + 必要 `.fbx`/纹理 | 保留可编辑场景、绑定和来源 | 只保存 GLB |
| 配方/清单 | 有版本号的 JSON Schema | 可读、可验证、适合随机化和前后端共享 | 数据库优先；自定义二进制 |
| 初期持久化 | Git 管理的 JSON + 文件目录 | 单用户本地工具足够，易迁移和审计 | SQLite；PostgreSQL |
| 前端测试 | Vitest + Playwright | 覆盖合同逻辑和关键交互路径 | Jest；仅人工测试 |
| Python 测试 | pytest + 现有验证脚本 | 适合脚本、清单和转换流程 | unittest |

## 关键架构边界

```text
Studio UI / Three.js
        │ 读取、编辑 Recipe JSON
        ▼
本地作业服务（验证、排队、日志）
        │ 调用固定版本脚本
        ▼
Blender 权威生成/绑定/渲染
        │ 输出 GLB、GIF、帧、报告
        ▼
workspace 候选 ──人工审查──> milestones 正式里程碑
```

- Three.js 是快速预览，不是最终几何真相。
- Blender 是模型、绑定和最终渲染的权威执行器。
- Recipe JSON 是前端、服务和 Blender 之间唯一共享业务合同。
- `workspace/` 与 `milestones/` 之间必须有人工作为晋级门。

## 已确认的第一版技术边界

1. 使用 React + TypeScript + Vite，并通过 React Three Fiber 集成 Three.js。
2. 第一版只支持 Windows 单用户本地运行。
3. 先用普通步骤和表单稳定 Recipe，再评估节点/蓝图编辑器。
4. 第一版不引入账号、云端数据库或多人协作。
5. 第三方许可证不明确的模型只存在于私有仓库与本地工具，不对外发布。
6. F001 已建立交互预览，F002 已建立单模型五步装配工作流；两者仍等待用户视觉验收后晋级。
