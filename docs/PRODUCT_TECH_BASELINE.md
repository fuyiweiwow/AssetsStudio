# AssetsStudio 产品与技术基线（讨论稿）

- 状态：`draft_for_discussion`
- 建立时间：2026-08-09
- 确认人：待用户确认

本文件用于同步“我们要做什么、为什么做、准备怎样做”。讨论完成前，以下技术选型均为建议，不是不可变决定。

## 我理解的产品目标

AssetsStudio 是一个面向 2D/像素化 Rogue 类游戏资产生产的本地工作流工具。它复用已验证的 Actor、骨骼动画、发型、五官、短袖、短裤和鞋里程碑，让用户能够预览、组合、参数化和随机化角色外观，并由 Blender 生成权威 3D 结果以及最终 Gallery、GIF、帧序列或像素素材。

它不是一个通用 3D 建模软件，也不以电影级真实布料模拟为首要目标。核心价值是：换机器仍可复现、可批量生成、结果直观可审查、适合最终 2D 游戏表现。

## 已明确的需求

1. 保留并使用当前正式身体、Walk/Run、发型、五官、短袖、短裤和鞋模型及工作流。
2. 前端使用 Three.js 显示角色和服饰的交互式 3D 预览。
3. 支持发型、五官和服饰的组合与可复现随机化。
4. 未来支持服装配方参数，例如袖型与袖长、领型与领口面积、下摆长度、材质和花纹；裤子和鞋采用同一可扩展思想。
5. Blender 负责权威几何生成、贴合、绑定、动作验证和最终渲染。
6. 每个视觉结果提供正面、侧面、背面以及运动 GIF，用户人工审查是正式晋级条件。
7. 正式仓库携带工作流依赖的模型、纹理、动作和重建脚本，避免环境迁移后依赖 AssetsLab。
8. 正式分支保持短小、当前和可追溯，过时实现及时清理并留下原因与恢复位置。

## 当前非目标

- 第一阶段不实现完整 Blender 替代品。
- 第一阶段不追求实时高精度布料动力学。
- 在配方数据结构稳定前，不优先开发复杂节点/蓝图编辑器。
- 不把自动穿模分数当作最终视觉验收。
- 不把旧 GarmentCode 失败实验重新引入正式基线；以后若重启该方向，必须以新功能提案和新证据开始。

## 建议的交付阶段

### Phase 0：开发基准

建立原则、功能文档、ADR、删除记录、时间线和自动验证。本文档对应此阶段。

### Phase 1：Studio 外壳与资产注册表

建立本地前端工程，读取统一资产清单，展示六类里程碑、状态、来源、预览和已知限制。先让“现在有什么”稳定可见。

### Phase 2：Three.js 角色预览

把权威 `.blend`/`.fbx` 通过可复现脚本导出为预览用 `.glb`，在前端加载 Actor、服饰和骨骼动画，支持镜头、正侧背视图、播放/暂停和组件开关。

### Phase 3：配方合同与表单编辑器

先用普通控件定义稳定的角色配方 JSON：随机种子、发型、五官、上衣、裤子、鞋、颜色和参数。验证合同后再考虑节点表示。

### Phase 4：Blender 作业桥接

本地服务接收配方，调用 Blender 无界面脚本，返回模型、验证报告、Gallery 和 GIF。作业应有日志、状态、可取消性和确定性输出目录。

### Phase 5：程序化模块扩展

逐项完善发型、五官、衣服、裤子和鞋的参数化与随机化。每类资产都沿用候选区、自动验证、人工审查、里程碑晋级的闭环。

### Phase 6：节点/蓝图编辑器

当配方字段和模块接口稳定后，再把同一数据合同映射为节点编辑器；节点层不重新定义一套与表单不同的业务模型。

### Phase 7：2D/像素导出

固化摄像机、灯光、动作、方向、帧率、像素化和打包规范，导出游戏可直接使用的帧、Sprite Sheet、GIF 和元数据。

## 建议技术选型

| 层 | 建议 | 原因 | 主要替代方案 |
| --- | --- | --- | --- |
| 前端语言/构建 | TypeScript + Vite | 类型约束配方与资产合同；启动快；适合本地工具 | JavaScript；Next.js |
| UI | React | 适合参数面板、资产库、状态视图和后续节点编辑 | Vue；原生 Web Components |
| 3D 预览 | Three.js，经 `@react-three/fiber` 集成 | 保留 Three.js 生态，同时让场景状态与 React UI 协同 | 直接 Three.js；Babylon.js |
| 节点编辑 | 后期评估 React Flow | 与 React 集成成熟，但应等配方合同稳定 | Rete.js；自建 Canvas |
| 本地服务 | Python + FastAPI | 可直接复用 Blender/Python 脚本，类型和作业 API 清晰 | Node 服务；仅 CLI |
| 权威生成 | Blender 无界面模式 + Python | 当前里程碑与脚本已经建立在 Blender 上 | 浏览器端几何；游戏引擎编辑器 |
| 预览格式 | GLB/glTF | 浏览器加载、骨骼动画和材质支持成熟 | FBX 在线加载；OBJ |
| 权威源格式 | `.blend` + 必要 `.fbx`/纹理 | 保留可编辑场景、绑定和来源 | 只保存 GLB |
| 配方/清单 | 有版本号的 JSON Schema | 可读、可验证、适合随机化和前后端共享 | 数据库优先；自定义二进制 |
| 初期持久化 | Git 管理的 JSON + 文件目录 | 单用户本地工具足够，易迁移和审计 | SQLite；PostgreSQL |
| 前端测试 | Vitest + Playwright | 覆盖合同逻辑和关键交互路径 | Jest；仅人工测试 |
| Python 测试 | pytest + 现有验证脚本 | 适合脚本、清单和转换流程 | unittest |

## 关键架构边界

```text
Studio UI / Three.js
        │ 读取、编辑 Recipe JSON
        ▼
本地作业服务（验证、排队、日志）
        │ 调用固定版本脚本
        ▼
Blender 权威生成/绑定/渲染
        │ 输出 GLB、GIF、帧、报告
        ▼
workspace 候选 ──人工审查──> milestones 正式里程碑
```

- Three.js 是快速预览，不是最终几何真相。
- Blender 是模型、绑定和最终渲染的权威执行器。
- Recipe JSON 是前端、服务和 Blender 之间唯一共享业务合同。
- `workspace/` 与 `milestones/` 之间必须有人工作为晋级门。

## 当前需要讨论确认的问题

1. 第一版是否采用 React，还是希望保持原生 Three.js/HTML 以减少抽象？
2. 第一版是否只支持 Windows 本机，还是从开始就要求 Windows/macOS/Linux？
3. Studio 第一版优先展示“资产库+组合预览”，还是优先打通“一个配方调用 Blender 并输出 GIF”的端到端闭环？
4. 是否接受先用表单稳定配方，再开发节点/蓝图编辑器？
5. 首个可交付版本是否只服务单用户本地运行，不引入账号、云端和数据库？
6. 第三方来源许可证不明确的鞋模型是否继续只允许存在于私有仓库与本地工具中？

讨论确认后，本文件状态改为 `accepted`，并为 Phase 1 创建第一份正式功能文档。
